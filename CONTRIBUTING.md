# Feedback and contributions

Keep changes focused and use synthetic or already-public examples. Include the
exact commit, environment, reproduction steps, and expected behavior in problem
reports. Use the feedback template for unclear claims or documentation.

Preserve scientific limitations, historical results, existing attribution, and
all current license boundaries. A documentation change must not imply a new
software release, benchmark result, endorsement, or archived DOI version.
Do not attach secrets, personal data, private observations, or raw private logs.

For code changes, run the validation commands in the README and report any
failures or skipped checks. Record the version and exact commit used when
citing development work; retain existing archive identifiers for the releases
they actually describe.
